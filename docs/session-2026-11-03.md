# seatmap: session notes, 3 November 2026

What we built in the backend (`seatmap-api`) today, the decisions behind it, and what comes
next.

---

## 1. The project

**seatmap** is a platform for designing seat maps (courts, arenas, stadiums, theatres, halls)
and selling tickets against them. The name was chosen today. We deliberately avoided
"venue-…" names, because the product shouldn't imply one kind of place.

| Project | Where | State |
|---|---|---|
| `venue-designer` | `projects/venue-designer` | The existing Angular seat-map designer. **Not in git yet.** It will become an Angular library. |
| `seatmap-api` | `projects/seatmap-api`, github.com/mansourtaok/seatmap-api (private) | The Spring Boot backend, built today. |
| `seatmap-web` | (later) | The Angular host app that embeds the designer. |

### Environment
- **Java 27** (Temurin, installed today; Java 21 is still there), **Spring Boot 4.1.2**,
  **Gradle 9.8** (Kotlin DSL, through the wrapper).
- **PostgreSQL 17.7**, already installed on the machine. It has two databases: `seatmap` (the
  app) and `seatmap_test` (the automated tests), both owned by the `seatmap` user.
- **Secrets are never in git.** The database password and the ticket signing key live in
  `config/application.properties`, which git ignores, or in the environment variables
  `SEATMAP_DB_PASSWORD` and `SEATMAP_TICKET_KEY`.

### How we work
Each step is **planned first and approved by you**: tables, flow, API and the open decisions.
Then it's built with automated tests, tried on the running app, and committed and pushed
when you say so.

## 2. Step 1: Layouts (commit `2bc7a30`)

**Idea:** each layout has one **editable draft**. **Publishing** turns the draft into a
numbered **version** that never changes again (v1, v2, …). Events sell a version, so a layout
that's selling tickets can't change under its buyers.

- The designer's whole document is stored as **JSON** (`jsonb`) in the database.
- When a version is published, its **inventory** is extracted: every seat, plus standing areas
  and sections sold by capacity. They're keyed by the designer's own ids, so a seat keeps its
  identity from one version to the next.
- **Saving needs the current revision.** A save based on an older copy (another browser tab,
  say) is refused with `409 Conflict` instead of overwriting newer work.
- **The server checks the data** (unique ids, seats and their table/row/stand pointing at each
  other, existing categories and images). Geometry rules stay in the designer.
- **Floor-plan images** are stored once and never changed, because published versions show
  them.

**Decisions you made:** every published version is immutable; one inventory table for seats
and standing areas; no login yet (it came in step 3); images stored in Postgres for now.

## 3. Step 2: Events and reservations (commit `7e5802a`)

- An **event** sells one published version, with its own prices (starting from the layout's
  defaults), currency and status: draft → on sale → closed, or cancelled.
- A **reservation** holds seats or standing places for **10 minutes**, then is
  **confirmed** (sold) or **released**. A hold is **all or nothing**: if one seat is taken,
  nothing is held, and the answer says which seat.
- **No double-selling:** the database itself allows only one holder per seat. Tested with 20
  buyers grabbing the same seat at the same moment (exactly one wins), and 12 buyers competing
  for a 5-place standing area (exactly 5 win).
- **The price is frozen at hold time.** Changing prices doesn't alter existing orders.
- **Live seat statuses** are served in exactly the format the designer's buyer view already
  understands.

## 4. Step 3: Login, organizations and roles (commit `326d688`)

### Who is who
- **Organizations** (venue operators, promoters) own layouts and events.
- **Members** have a role:
  `VIEWER` (read) < `SCANNER` (check tickets in, added in step 4) < `EDITOR` (edit, publish,
  prices, box office) < `ADMIN` (members, deleting layouts).
- **Buyers have no account** (guest checkout).

### Why session cookies rather than tokens (your question)
Both are "tokens" in a sense. The difference is where login state lives and who can read it.

| | Session cookie (chosen) | JWT token |
|---|---|---|
| Can a script on the page steal it? | **No**: `HttpOnly` | Yes, if it's kept in the browser |
| Logout, role change, account lock | **Applies immediately** | Only once the token expires |
| Extra work | Very little | Refresh tokens, rotation, key management |
| Costs | CSRF protection (included), works best on one domain | — |

Tokens suit mobile apps, public APIs for third parties, and many separate services. Spring can
accept both later, so starting with cookies doesn't lock us in.

### What was built
- Signup creates **your own organization** (open signup). Passwords are bcrypt hashes (10+
  characters). **10 failed logins lock the account for 15 minutes.**
- Sessions live in Postgres, so a restart doesn't log anyone out. CSRF protection uses the
  `XSRF-TOKEN` cookie, which Angular handles by itself.
- **Another organization's data answers "not found"**, so nobody can probe which ids exist.
- **Role changes apply on the next request.** An organization always keeps at least one admin.
- **Guest limits** (anti-bot): at most 10 holds a minute and 20 places held at once, per IP
  address per event. Staff aren't limited.

### Decision: only staff can confirm a sale, for now
Confirming means "the money arrived". Until payments exist, a buyer who could confirm would get
seats without paying. So confirm needs `EDITOR`, which also gives a real **box-office** flow.

### Your clarification on payments
When creating an event, the organizer chooses **our payment gateway** (we collect, take a fee,
pay them out) or **their own gateway** (the money goes straight to them). In both cases the
gateway notifies our server ("payment succeeded") and **the server confirms**. The buyer never
does.

## 5. Step 4: Tickets (commit `1bfece1`)

### Your question: how does a buyer without an account get the PDF?
"No account" doesn't mean "no email". At checkout the buyer gives a **name and email**. After
payment they get the tickets three ways: **download** on the confirmation page, **by email**
(PDF attached), and **"find my tickets"** (enter the email and they're sent again).

### What was built
- **Confirming issues the tickets:** one per seat, and one per standing place ("General Floor
  · Place 2 of 3").
- **A PDF** with one A4 page per ticket: event, local date and time, seat, category, price,
  venue, buyer, order number, and a large **QR code**.
- **Signed QR codes:** the ticket id plus a cryptographic signature (HMAC) made with a server
  secret. They can't be forged, and they aren't stored, so a leaked database contains no usable
  tickets. **Changing the secret invalidates every ticket.**
- **Check-in at the door** answers *valid*, *already used (at 19:42)* or *not valid*. Ten gates
  scanning the same ticket at once let it in exactly once.
- **The `SCANNER` role** (your question 3) is for door staff: they can scan and see arrival
  counts, but can't edit, sell, change prices or undo a check-in. That keeps a temporary
  worker from letting someone in twice or changing anything.
- **Email goes through an outbox** with automatic retries, so a sale never ends up without its
  email because of a network problem. During development, emails are saved as `.eml` files in
  `build/mail/` instead of being sent.
- **Email is optional at the box office** (print on the spot) and will be required online.
- Events now have a **time zone** (for example `Europe/Paris`), so tickets print local time.

## 6. Problems found and fixed along the way

- An image upload sent as `image/png;charset=UTF-8` was rejected; it's now accepted.
- The event currency column type didn't match what the app expected, so the app wouldn't start.
- The session table couldn't store the logged-in user; the user is now stored by id.
- The `XSRF-TOKEN` cookie wasn't sent until something asked for it, which Angular needs up front.
- The test tool (MockMvc) doesn't show cookie flags, so those are now tested on a real server.
- A ticket code could be written more than one way. Now only the exact code issued is accepted.
- Some tests failed randomly, because a background job in one test setup took work from
  another's. Tests now run those jobs themselves.

## 7. Known limitations and open items

- **The PDF font covers Western European text only.** Arabic and other scripts print as "?"
  until a Unicode font (and, for Arabic, letter shaping) is added.
- **No email service yet**, so there's no password reset or member invitations by email.
  Members must already have an account to be added.
- **In production:** set `server.forward-headers-strategy` behind a proxy (otherwise all
  guests share one limit), `SEATMAP_SECURE_COOKIES=true` over HTTPS, and a real
  `SEATMAP_TICKET_KEY`.
- **Not built yet:** refunds or voided tickets, moving an event to a newer layout version,
  Apple/Google Wallet, a scanner app, buyer accounts.
- **The designer** isn't in git yet, and isn't connected to this API yet.
